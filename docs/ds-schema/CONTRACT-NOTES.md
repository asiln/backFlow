# Contract notes (T1): ambiguities in spec section 7 and how the schemas resolve them

Schemas: `docs/ds-schema/*.schema.json` (draft 2020-12). Validate with `tools/ds/common/validate.mjs` (`validate(name, data)`, names: `node cmp tok screen-file library inventory config tokens decisions`)
or `npm run validate:ds`. Fixtures: `fixtures/ds/`. When one of these resolutions is wrong, change the schema AND the fixture generator (`fixtures/ds/build-fixtures.mjs`) together.

## A. Fields missing from, or conflicting in, section 7

1. **Top-level marker.** README/`extract.mjs` write `figmaLift: 1`. `screen-file` requires it; enriched files add `ds: { library, tokens, ver: 1 }`.
2. **`TokRef` has no field for icon (svg) colours or shadow colours** although 4.1 harvests them (role `icon`, `shadow`). Added `ic` (svg root colour key). Shadow colours need no field: they are part of the effect key `e`. `sw` (stroke weight) stays in `TokRef` but no harvest family produces it (4.1 has no `sw:` key), so fixtures never write it.
3. **Icon refs.** 3.3 shows `cmp: { id: 'ic_...', kind: 'icon', c: 'icon/dim', sz: 16 }` but 7.1 `CmpRef` has neither `kind` nor `c`, and `sz` is `[w,h]` there. Resolution: `CmpRef.kind?: 'component'|'icon'` (default component), `CmpRef.c?` = **colour token key** (`c:6b7280@100`, not a variable name) written only when the instance colour differs from the library icon's `dominantColor` and has a live token; `sz` stays the `[w|null, h|null]` tuple (an icon's render size is the node's own `w`/`h`, so no extra field). `Override.ic` keeps its own `c` and numeric `sz`.
4. **`Override` is not discriminated.** Every member has `s` plus optional fields, and the `fill`/`stroke` variant has no required key besides `s`. Schema: `anyOf` of six strict variants, each `additionalProperties:false`, so exactly one payload kind per override (`t[,r]` | `b` | `ic[,c,sz]` | `img` | `fill|fillTok|stroke|strokeTok|op` (>= 1) | `v`). An override with `{s}` only, or `{s, t, b}`, is invalid. The text variant also accepts `r` (runs) as the 7.1 comment says.
5. **Slot id semantics.** 7.1 calls `s` "string path, `'2'` or `'2.1'`" while 7.2 slots carry both `s` and `path: number[]`. Resolution: `slots[].s` is the slot's index in `slots[]` as a decimal string (DFS order of the master); `path` is the child-index path of the node in `root`; an override addressing a slot inside a nested instance is `'<outer inst slot>.<inner slot>'` (`"3.2"` = inner slot 2 of the nested instance held by outer slot 3). Several slots may share a `path` (Button: `Show icon` bool and `Icon` swap both point at the icon node). The outer slot must have `kind: 'inst'`.
6. **Nested instance information is stored twice.** The parent's dotted overrides (`3.2`) and the nested node's own `cmp` in the retained `children` carry the same facts. Rule: the plugin applies the parent's `ov` when it instantiates the parent; the nested `cmp` is authoritative when a consumer builds from `children` (R3 fallback, `expand.mjs`). `scripts/validate-ds.mjs` does not require them to be equal, `expand.mjs` (T8) should.
7. **Optional parts.** `root` of a `LibComponent` is the SUPERSET exemplar (every optional node present). Visibility in the default master comes from the `default` of the `bool` slot (fixtures: `Show icon` default `false`). Variant `members[].root` are supersets too.
8. **`tokens.json` colour entries are unique per (key, role).** 4.1 says "per key with roles histogram" but 4.2 snaps `l.role === e.role` and 4.4 gives one `target` per key, while the same colour is legitimately `bg/surface` as a fill and a different variable as text/icon. Resolution: one entry per `(key, role)`; `role` is required; `roles` is an optional histogram kept for readability. A `TokRef` field implies the role (`f`=fill, `s`=stroke, `tx`=text, `ic`=icon). Non-colour families (text, radius, spacing, effect, size) have no role; spacing uses from `ls.g/g2` and `ls.p` merge into one `sp:` entry.
9. **Key formats not fully specified.** Fixed in `tools/ds/common/keys.mjs`: text `t:<family>/<size>/<weight>/<lh px>/<letter-spacing em, 3 dp>`; radius `r:16` (collapsed) or `r:tl/tr/br/bl`; spacing `sp:<n>`; size `sz:h<n>`; effect `e:` + stack joined by `|`, each `[i]x,y,blur,spread,rrggbb@aa` (the 4.1 text says `inset,x,y,blur,spread,colorKey`, the 4.4 example omits inset and the `c:` prefix; the `i` prefix appears only for inset shadows); colour `c:rrggbb@aa` with `aa = round(alpha*100)`.
10. **Padding keys** `p` are `[t,r,b,l]`, each `sp:<n>` computed after subtracting `ls.bw`, `null` for 0 or untokenised sides; the field is omitted when all four are null.
11. **`tok` only references live tokens.** A key is written only for status `bound|create|review`; `skip`/`off-scale` values are not referenced and stay literal. (4.4 lists the statuses but not this consequence.)
12. **Alpha variant names.** 4.3/4.6 show `tint/accent-10`, `tint/accent-15`, `border/accent-40`: inconsistent prefixes. Resolution used by the fixtures: `<mapped name>-<aa>` (`bg/scrim-40`), no `tint/` prefix, unless `tokenMap` maps the full name. T2 may refine, but then update `tokens.json` fixtures.
13. **`inventory.variables[].name` vs `tokens.existing.name`.** 4.4's example shows `existing.name: "Color/bg/surface-2"` (collection-prefixed) while `target.name` is `bg/surface-2` and 7.3 has a separate `collection`. Resolution: inventory `name` has no collection prefix; `collection` is a collection id; `existing.name = "<collection name>/<variable name>"`. `valuesByMode` is keyed by **mode id** (see `collections[].modes`); colours are `{r,g,b,a}` floats; aliases `{type:"VARIABLE_ALIAS", id}`. `fingerprint` is only prose in 2.8.1: schema = recursive `{t,k,s,kids,fills,radius,h,pad,gap}` (all optional, extra keys allowed) or `{variants:{"Prop=Value, ...": fingerprint}}` for sets.
14. **`ds.variantMap` type.** `Record<string,string>[]` does not say what an entry maps. Resolution: each element is one pair `{ "<our variant name>": "<DS variant name>" }` (`"Type=Primary, State=Default": "Style=Accent, State=Default"`).
15. **`component-decisions.json` has no shape in the spec** (1.9 names the verbs only). Defined in `decisions.schema.json`: `{version:1, decisions:[{id|sig, action: accept|reject|rename|merge|split|variant-of, name?, group?, into?, by?, props?, note?}], exclude?}` with per-action requirements (rename needs `name`, merge/variant-of need `into`, split needs `by`).
16. **`ds.config.json`.** 7.4 has `thresholds.{occ,screens,minConf,colorDeltaE,alphaTol}` but 1.5 also uses "tiny node < 6 needs 4" and 4.4 uses `minUses`/`minScreens`; added `occTiny`, `tinyNodes`, `minUses`, `minScreens`. The `<Role>` part of `Text/<Role> <size> <Weight>` (4.5/4.6) has no source, so `textStyleNames` (key -> style name) was added. `nameHints.groups` (component name -> group) added for 1.6's "defaults from role". Unknown top-level keys are rejected unless they start with `x-`.
17. **`tokens.json` extras.** Optional `sizes[]` (4.1 harvests `sz:` but 4.4 shows no array) and `candidates[]` on `review` colour entries.
18. **Library extras.** `LibComponent.sig` (optional, S+M hash used as plugin data in 2.1). `band` is only `auto|review` (report-only clusters are never in `_library.json`; they live in `components-report.json`). `nameSource` has `owner` and `aria`, which the confidence formula (1.9) does not weight: treat `owner` as 1.0 (decisions set conf 100) and `aria` like `role` (0.9) unless the detector defines otherwise.
19. **Who writes `tok` into enriched files?** 5 says `componentize.mjs` "adds cmp/tok", 10 says T2 delivers `annotate.mjs` as a writer module and 5 says tokens.mjs keeps annotations "in memory". Resolution: `annotate.mjs` is a library; `componentize.mjs` calls it when writing `out/enriched/*.figma.json`; `tokens.mjs` alone only writes `tokens.json`. Library roots carry `tok` too (same function).

## B. Digest / clustering ambiguities (hash.mjs, spec 1.2-1.4)

20. **S includes the root's own `ls.s` pair ("as a child")**, so a hug-width Button and a fill-width Button (`['H','H']` vs `['L','H']`) never share an S bucket, which contradicts the goal "358px and 200px wide Buttons are one component" (2.3 sizes each instance independently). `digestView(view, { ignoreRootSizing: true })` drops the root pair; default follows the spec. Recommend T4 enable it for candidate roots (children keep their pairs).
21. **S prose vs code.** Prose lists `pos`, the code does not; text leaf S omits sizing. Implemented: `pos` included (`p<fixed|sticky>`), leaf S has no `ls.s`, leaf S gets a `^` suffix when out of flow.
22. **Text `single|multi` is content-dependent** (line count changes with label length), so a Button with a wrapping label can land in a different S bucket. Implemented as specified; if it splits real clusters, make `multi` depend on `nw`/`tr` only.
23. **Hash vs tolerance.** M quantises (`q`, `q2`) so near values straddling a bin edge hash differently; tolerance merging must therefore run on `digest.slots` (`slotsClose`/`slotsDistance`) inside an S bucket, never on M equality. The slot vector order is fixed by `ownSlots` (frame: g, g2, p[4], radius[4], strokeW[4], shadows x5 each, w/h only on `F` axes; vectors of unequal length never match).
24. **Nested instance leaf.** 1.2 says `C:<id>` for S and "M/P = its dev only". Implemented: M = hash of nothing, P = hash of the variant map (so different nested variants stay visible in P, 1.7). Build such views with `makeView(node, { collapse: true })`.
25. **Paint tolerance with token keys.** "Equal if same tok key; else dE <= 1.5 and |dAlpha| <= 0.02": `paintsClose` compares role by role, equal keys short-circuit, otherwise colours (token keys are parsed back to RGBA). "CIEDE76" in 1.4 is CIE76; both `deltaE76` (default, metric `'76'`) and `deltaE2000` (`metric: '2000'`) exist.
26. **Alpha quantisation grid.** `quantAlpha` rounds to 0.02 bins, so 0.50 and 0.51 can fall into different bins (edge effect); only the hash is affected, `coloursClose` uses the real tolerance.
27. **Component ids** use the S of the master root (the superset for components with optional parts), not of a particular leader instance, so adding/removing an occurrence with the optional part does not change the id.

## C. Not resolvable from the spec (left for owners)

* `geom` of icons: fixtures use `hashStr(path data)`; T5 defines `iconSig` and must regenerate `fixtures/ds` if it differs.
* Element ordering of `cmp.ov` is the slot order; consumers must not depend on it.
* `stats.devMean/devMax` units are "px-equivalents" (max slot deviation); `ls` deviations are raw em values.
* `components-report.json` has no schema yet (not in section 7).
